  conversation. Cmd-A is really the only way to get the conversation?           
⏺ No, Cmd-A isn't the only way. Long conversations in claude.ai load messages as
  you scroll, so Cmd-A only picks up the part currently on the page. That's
  probably why some of yours is missing. There are three ways to get the whole
  thing:

  1. Data export (most reliable). In claude.ai, go to Settings → Privacy →
     Export data. You'll get an email with a download link to a zip file. Inside
     is conversations.json, which holds every conversation in full. Tell me
     where you saved it and which conversation it is (its title or date). I'll
     write a short script in the scratchpad that turns that one conversation
     into a plain-text file at other/llm_usage/00-claude-browser-chat.txt, with
     each message labelled by who wrote it. The email can take a few minutes to
     arrive.
  2. Scroll, then copy. Scroll all the way to the top of the conversation and
     wait until every message has loaded, then select and copy. This is quicker
     but easy to get wrong on a long chat, so check that the first and last
     messages are in the file.
  3. Share link, as a supplement only. The Share button creates a public link to
     a snapshot of the conversation. You could add it to the README, but still
     include the text file, because the full chat is supposed to be in the usage
     files.

❯ "so the four add up as squares" please explain                                
  ⎿  ⧉ Selected 1 lines from scripts/00-simulate_data.py in PyCharm

⏺ It means the spreads combine through their squares, which are the variances,
  rather than adding directly. That's the Pythagorean rule for independent
  random quantities.

  The rule. If independent random parts are added together, their variances add:

  $$\text{SD}_\text{total} = \sqrt{0.30^2 + 0.34^2 + 0.60^2} = \sqrt{0.09 +
  0.116 + 0.36} \approx 0.75$$

  So a single simulated result on the log10 scale varies around its beach
  baseline with a standard deviation of about 0.75. Adding the SDs directly
  would give 1.24, which overstates it, because the parts partly cancel: a wet
  city-wide day may coincide with a lucky low sample at one site.

  Two details in that comment:

  - "Four parts", but only three are random. The beach baseline (1.10, plus 0.2
    or 0.4 for the raised beaches) is a fixed number. It shifts every result
    from that beach up or down but adds no spread. So the comment is slightly
    loose: the three random parts add as squares, and the baseline just sets the
    centre.
  - "Once the carry-over has settled down." The two daily effects each carry
    half of the previous day's value into the next day (CARRY_OVER = 0.5). If
    each day's new random input had an SD of 0.30, the carried-over part would
    pile on top, and the day-to-day effect would end up with an SD larger than
    0.30. To avoid that, line 136 shrinks each day's new input:

    $$\text{input SD} = 0.30 \times \sqrt{1 - 0.5^2} \approx 0.26$$

    The carried-over half (variance $0.5^2 \times 0.30^2$) plus the new input
    (variance $0.26^2$) then add back up to exactly $0.30^2$. So CITY_SD = 0.30
    really is the spread of the city-wide effect on any given day, after the
    first few days. That is what makes the three SDs in the formula above add
    correctly.

  In short, each SD in the settings is the part's own spread, chosen so that the
  squares add to the total spread seen in the real data.

❯ so polars has when/then/otherwise?  why not if/then/else?                     

⏺ Python's if/else chooses between two things based on a single True or False. A
  Polars condition such as pl.col("eColi") > 100 isn't a single True or False.
  It's an expression that Polars will evaluate for every row later, giving a
  whole column of True/False values. So Python has nothing to branch on:

  if pl.col("eColi") > 100:   # error: the truth value of an Expr is ambiguous
      ...

  when/then/otherwise builds a row-by-row choice into the expression itself:

  pl.when(pl.col("eColi") > 100).then(pl.lit("over")).otherwise(pl.lit("under"))

  Polars then runs that choice across the whole column at once, which is also
  much faster than a Python loop over rows. It's the same idea as
  np.where(condition, a, b) in NumPy, or CASE WHEN … THEN … ELSE … END in SQL.

  As for the names, if and else are reserved words in Python, so they can't be
  used as method names like pl.if(...). Polars borrowed when/otherwise from
  Spark, which borrowed from SQL's CASE WHEN.

✻ Sautéed for 7s · done 11:04 AM

❯ that's cool. does pandas have the same thing?                                 
⏺ Not with the same names, but pandas can do the same job in a few ways:

  - np.where is the most common, for a single condition:

  df["status"] = np.where(df["eColi"] > 100, "over", "under")
  - np.select handles several conditions, like chaining when several times in
    Polars:

  df["level"] = np.select(
      [df["eColi"] > 1000, df["eColi"] > 100],
      ["very high", "over"],
      default="under",
  )
  - Series.case_when, added in pandas 2.2, is the closest to Polars. The first
    condition that is true wins:

  df["level"] = df["eColi"].case_when([
      (df["eColi"] > 1000, "very high"),
      (df["eColi"] > 100, "over"),
      (df["eColi"] <= 100, "under"),
  ])

    Rows that match no condition keep their original value, so the last
    condition acts as the else.
  - Series.where and Series.mask keep values where a condition holds and replace
    the rest, or the reverse. The names are confusing, because where keeps the
    values where the condition is true, the opposite of what people often
    expect.

  All of these work row by row across the whole column, just like Polars. The
  difference is that pandas computes the result immediately, whereas a Polars
  expression is built first and run later, which lets Polars optimise the whole
  query.

❯ I don't understand why simulate is before download and clean!                 

⏺ The idea is to decide what you expect before the real data can influence you.
  Simulating first has four benefits:

  1. It forces you to think through the data before you have it. To simulate,
     you have to decide what a row is, which columns exist, what range the
     values take and how they relate to each other. That's the sketch step
     turned into code.
  2. Your tests are honest. If you write the tests on simulated data, they
     express what the data should look like. If you write them after seeing the
     real data, it's easy to write tests the data already pass, and then they
     check nothing.
  3. Your analysis isn't chosen by its results. Building the analysis code on
     fake data means you choose the method before you know which choice gives
     the most striking answer. It works like registering a clinical trial's
     analysis plan before unblinding. Otherwise you can try many analyses and
     keep the one that "works" without meaning to.
  4. You have a known answer to check against. Only simulated data let you check
     that the method recovers differences you built in. That's your Appendix B.

  There's also a practical reason. In many real projects, the data arrive late
  or need permission, and simulating lets you write all the code while you wait.

  The tension you ran into is real. To simulate well, you need to know things
  like the floor at 10 and the ceiling at 1,000, and you only learned those by
  looking. For an unfamiliar dataset, a quick look first and then simulate, test
  and analyse, as you did, is a sensible compromise. The principle that matters
  is that the analysis plan was written and checked on simulated data before
  you saw the results, and you did that.

⏺ I think that's a sound distinction, and it matches how the research world
  treats the two kinds of study.

  In a retrospective study, the useful line is between looking at the data's 
  structure and looking at its answer. You needed the structure to simulate
  well: the floor, the ceiling, the blanks, the number of sites. Seeing that
  doesn't bias the analysis. What does bias it is seeing the result you care
  about, here which beaches are worse and how often the sign is right, before
  the method is fixed. So a retrospective protocol could be:
  1. Explore the structure and the measurement process only.
  2. Simulate, including the quirks you found.
  3. Write the tests and the analysis, and check them on the simulated data.
  4. Only then run the analysis on the real data.

  The same idea exists elsewhere under other names:
  - The Open Science Framework has a preregistration template for secondary
    data, meaning data someone else already collected. It asks you to state what
    you have already seen or analysed before registering.
  - Particle physicists use "blind analysis". They hide or shift the quantity of
    interest while tuning the method, then reveal it once the method is frozen.

  In a prospective study, simulation does extra work. Besides fixing the
  analysis in advance, it lets you plan the study. You can ask how many samples
  or sites you need to detect a difference of a given size, which is a power
  analysis done by simulation. You can also check whether your measurement
  method has a floor that would hide the effect you're looking for. For a
  retrospective study, the sample is already fixed.

  Your project also shows a benefit specific to retrospective work. Because you
  knew the real quirks, the simulation could measure their cost: about 65% of a

  looks the way you expect before you trust any analysis built on it. It was
  written by Posit, the company behind RStudio, and started as an R package.

  scripts/01-test_simulated_data.py:

  validation = (
      pb.Validate(data=simulated_data, label="Structure and values")
      .col_schema_match(...)             # the right columns, in order, with the
  right types
      .col_vals_in_set(columns="beachName", set=EXPECTED_BEACHES)   # only the 
  ten real beaches
      .col_vals_ge(columns="eColi", value=10, na_pass=True)         # nothing 
  below 10; blanks allowed
      .rows_distinct(columns_subset=["siteName", "collectionDate"]) # one sample
  per site per day
      .interrogate()                     # run all the checks
  )

  .interrogate() runs every check and records how many rows passed and failed
  each one. It also produces the summary table printed at the end of the test
  scripts. The unusual method name is why "interrogate" came up in the
  banned-word scan.

  Why use it rather than plain assert statements:
  - The checks read like a description of the data, which doubles as
    documentation.
  - It counts failures instead of stopping at the first one. If 3 rows out of
    98,000 break a rule, you see which rule and how many rows, rather than a
    single crash.
  - Thresholds are possible. You can allow, say, up to 1% of rows to fail a
    check before it counts as a failure. That suits messy real data.
  - It works directly with Polars, which is what the project uses.

  The rubric names pointblank among the recommended testing tools, alongside
  testthat, validate and great expectations, which is why the project uses it.
  The simulated data have 16 checks and the cleaned data 22.

❯ please explain the ratio and why poisson count would give about 1             

⏺ The ratio. For each beach and year, count the days over the limit. That gives
  200 counts: 10 beaches over 20 years. Then calculate two numbers:
  - Mean: the average count, for example 10 days a year.
  - Variance: how much the counts spread around that mean, measured as the
    average squared distance from it.

  The ratio is variance ÷ mean, sometimes called the dispersion index.

  Why a Poisson count gives about 1. A Poisson distribution describes counts of
  events that happen independently at a steady rate, like radioactive decays in
  a minute. A mathematical property of the Poisson distribution is that its
  variance equals its mean. So if the mean is 10 days a year, the variance is
  also about 10, and the ratio is about 1.

  Here is the intuition, with a beach of about 100 sampled days a year and a 10%
  chance that any day goes over, each day independent:
  - The expected count is 10 days.
  - By chance, some years give 7 and some give 13. The typical spread is about
    $\sqrt{10} \approx 3$ days, so the variance is about $3^2 \approx 10$,
    matching the mean.

  Strictly, the days form a binomial count (a fixed number of yes/no days),
  whose variance is $np(1-p) = 100 \times 0.1 \times 0.9 = 9$, giving a ratio of
  0.9. That's slightly under 1, and close to Poisson when the chance per day is
  small.

  What pushes the ratio above 1.
  1. Clustering (carry-over). If bad days come in runs, a wet week can add five
     days over the limit in one go. Counts then jump in chunks rather than one
     day at a time, so some years end up much higher and others much lower. The
     variance rises and the mean stays the same.
  2. Mixing different beaches. Pool a beach averaging 30 days a year with one
     averaging 5, and the counts range from about 5 to 30. That huge variance
     comes from the beaches being different, not from anything within a beach.
     This is why the pooled ratio (4.7 simulated, 8.7 real) mostly measures the
     differences between beaches, whereas each beach on its own (0.9 to 1.9
     simulated) shows the effect of clustering alone.

  Put simply: a ratio of about 1 means the days are behaving like independent
  coin flips. Well above 1 means something is bunching them together, either
  runs of bad weather or, when the beaches are pooled, the beaches themselves.

❯ why aren't we using requests to download the data?                            

⏺ No strong reason. The job is small enough that Python's standard library
  covers it. The script makes two requests:

  1. The package lookup: urlopen(...) from urllib.request, which is built into
     Python, fetches the JSON listing the dataset's files.
  2. The CSV itself: pl.read_csv(csv_resource["url"], ...). Polars downloads the
     file straight from the URL, so no HTTP library is needed at all.

  Using urllib means one fewer package to install and pin. requests is not in
  pyproject.toml.

  requests is the more common choice. The sample code on Open Data Toronto's
  pages uses it, which is probably why you expected it. It's nicer to work with:
  - response.raise_for_status() makes the error check explicit.
  - timeout= is easy to set.
  - response.json() parses the JSON in one step.
  - Sessions and retries help when making many calls.

  For two simple requests, those features don't add much. urlopen already raises
  an error on a failed response such as 404 or 500, so a broken download stops
  the script rather than saving an empty file. The only thing it lacks is a
  timeout, so a server that never answers would leave the script waiting. That's
  fine for a script you run by hand.

  I'd leave it as is. Both are standard, and switching would add a dependency on
  submission day without changing the result.

❯ what is the code from 133-138 doing?                                          

  Read 1 file (ctrl+o to expand)

⏺ Those lines convert each site's longitude and latitude, which are angles in
  degrees, into flat x and y coordinates in metres. That lets the points line up
  with the map tiles drawn underneath.

  Why it's needed. The background map comes from Esri via contextily as web map
  tiles, the same kind Google Maps uses. They're drawn in a projection called
  Web Mercator (code EPSG:3857), which flattens the round Earth onto a square
  grid. To place the sampling sites correctly on those tiles, their coordinates
  have to be in the same projection.

  The formulas (R = 6,378,137 m, the Earth's radius at the equator):

  - x (east–west): $x = R \times \text{longitude in radians}$

    Longitude becomes distance around the equator. Line 136 does this.
  - y (north–south): $y = R \times \ln\left(\tan\left(\frac{\pi}{4} +
    \frac{\text{latitude in radians}}{2}\right)\right)$

    Line 137 does this. It stretches north–south distances more and more as you
    move away from the equator. That's why Greenland looks as big as Africa on
    web maps. The stretching keeps shapes and angles correct locally, which is
    what makes the map look right when you zoom in.

  Two details:
  - np.radians(...) is a NumPy function, but it works on a Polars expression
    here because Polars lets NumPy functions act on its columns directly.
  - At Toronto's latitude, one of these "metres" is about 0.72 real metres:
    every direction is stretched by $1/\cos(43.65°) \approx 1.38$. That doesn't
    matter for a map, because the points and the tiles are stretched the same
    way. It does mean these x and y values shouldn't be used to measure real
    distances.

  A library such as pyproj or geopandas could do the conversion in one call.
  Writing the two formulas directly avoided adding another dependency just for
  this.

⏺ It's .cut, a Polars expression method called on the column (not pl.cut). It
  sorts continuous values into bins, like the bars of a histogram.

  How it works. You give it the edges between bins, and it returns a label for
  each value saying which bin it fell in. Five edges make six bins:

            30      100      300     1,000    3,000
     bin 0  |  bin 1 |  bin 2 |  bin 3 |  bin 4 |  bin 5
     ≤30     30–100   100–300  300–1k   1k–3k    3k–10k

  The details in lines 342–350:
  - Edges on the log scale: the values being binned are logGeometricMean, so the
    edges are np.log10([30, 100, 300, 1_000, 3_000]) as well. Each step is
    about half an order of magnitude ($10^{0.5} \approx 3$), so the bars are
    evenly spaced on a log axis.
  - Upper edge included: by default a bin includes its upper edge. Here's a
    small example:

  pl.Series([1.0, 1.9, 2.0, 2.1]).cut([1.5, 2.0], labels=["a", "b", "c"])
  # → ["a", "b", "b", "c"]   2.0 falls in "b", not "c"

    So a day with a geometric mean of exactly 100 lands in "30–100", which
    counts as not over the limit. That matches the rule of "over 100" used
    throughout the paper, and the comment on line 339 says so.
  - Numbers as labels: cut only accepts text labels, so the code labels the bins
    "0" to "5" and then .cast(pl.Int8) turns them into the numbers 0 to 5. The
    plotting code uses those numbers as bar positions, and BIN_LABELS supplies
    the readable names on the axis.
  - Open-ended outer bins: the first and last bins have no outer edge.
    Everything below 30 goes in bin 0, including the 17 days below 10 that the
    comment mentions. Everything above 3,000 goes in bin 5, labelled
    "3,000–10,000". I checked that label: the highest daily geometric mean in

❯ explain 97-119                                                                

  Read 1 file (ctrl+o to expand)

⏺ fit_beach_model fits the model in the paper's Equation 1. It has three steps.

  1. Line 115: subtract each day's average.
  It calls _relative_to_day (lines 85–94). For every beach-day, that takes the
  log10 geometric mean and subtracts the average of all beaches sampled that
  same day:

  pl.col("logGeometricMean") -
  pl.col("logGeometricMean").mean().over("collectionDate")

  .over("collectionDate") means "calculate the mean within each date, and put it
  back on every row of that date". The result, relativeToDay, is
  $\log_{10}(G_{bd}) - \bar{L}_d$ in Equation 1. A city-wide storm raises every
  beach that day, so it cancels out. Line 93 also strips spaces and apostrophes
  from beach names ("Ward's Island Beach" becomes "WardsIslandBeach") because
  the formula tool can't handle them.

  2. Line 116: fit the model.

  smf.ols("relativeToDay ~ beach - 1", data=prepared.to_pandas())

  - smf.ols is statsmodels' ordinary least squares regression, written as a
    formula. statsmodels needs a pandas table, hence .to_pandas().
  - relativeToDay ~ beach means "explain the daily gap by which beach it is".
    beach is a category, so each beach gets its own coefficient.
  - - 1 removes the intercept, the usual baseline term. Without it, one beach
    would be the reference and the others would be measured relative to it. With
    it removed, each beach's coefficient stands on its own.

  With only a category as the predictor, each coefficient works out to the
  average of that beach's daily gaps. That's $\beta_b$: 0.34 for Marie Curtis
  Park East, which is $10^{0.34} \approx 2.2$ times the average beach.

  3. Lines 117–118: clustered standard errors.
  The coefficients don't depend on this step; only their uncertainty does.
  - A normal standard error assumes every day is an independent piece of
    evidence. But a wet week raises a beach for several days running, so 7 bad
    days in a row are closer to one piece of evidence than seven.
  - cov_type="cluster" with groups=groupMonth handles this. Each month of each
    year (July 2019, August 2019, …) becomes one group. The uncertainty is
    estimated from how much the groups differ from each other, which allows any
    amount of correlation between days inside a group.
  - There are 60 groups: 20 years × 3 months. The few days in late May are
    merged into June, and the few in early September into August (lines
    108–109).
  - This roughly doubles the width of the intervals compared with treating each
    day as independent, as the Methods section says.

  The caveat in lines 111–113. Subtracting each day's average quietly uses up
  information, about one piece per sampling day. The model doesn't know that, so
  it thinks it has slightly more independent data than it does. Because
  clustered standard errors are driven by the 60 groups rather than the ~19,000
  rows, the effect on the intervals is small.

❯ why use holm instead of the other options?                                    
⏺ Holm's method was the best fit because the paper makes a strong claim, and
  Holm is the safest way to back it up with this model.

  What the paper claims. It says "Two beaches differ significantly". With 45
  pairs, that needs control of the chance of any false difference among them,
  called the family-wise error rate. The paper promises to keep it near 5%.

  The main options:

  Method: None
  What it controls: Each test at 5%
  Problem here: About 2 false differences expected among 45 pairs
  ────────────────────────────────────────
  Method: Bonferroni
  What it controls: Any false difference
  Problem here: Valid but too strict: every pair must have p < 0.05/45 ≈ 0.001,
  so real differences get missed
  ────────────────────────────────────────
  Method: Holm
  What it controls: Any false difference
  Problem here: None. It's never less powerful than Bonferroni, gives the same
  guarantee, and makes no assumptions about how the tests relate
  ────────────────────────────────────────
  Method: Tukey's HSD
  What it controls: Any false difference, for all pairs of means
  Problem here: Assumes independent observations with equal spread, which the
  month-clustered standard errors are there to avoid
  ────────────────────────────────────────
  Method: Benjamini–Hochberg
  What it controls: The share of false differences among those declared
  Problem here: A weaker promise. It allows some false differences, which suits
  screening many candidates, not claims about specific pairs
  ────────────────────────────────────────
  Method: Šidák, Hochberg
  What it controls: Any false difference
  Problem here: Rely on the tests being independent or positively related.
  That's
  plausible here, but it would need justifying

  How Holm works. Sort the 45 p-values from smallest to largest. Compare the
  smallest with 0.05/45, the next with 0.05/44, then 0.05/43, and so on,
  stopping at the first one that fails. Every pair before that point differs,
  and every pair from there on doesn't. After each success the bar is lowered a
  little, which is why it finds more differences than Bonferroni.

  Why it fits this analysis. The 45 comparisons are correlated: every pair
  shares the same days, and each beach appears in 9 pairs. The p-values also
  come from clustered standard errors. Holm's guarantee holds whatever the
  correlation and whatever produced the p-values, so nothing extra needs
  checking. Appendix B's simulation confirmed it: none of the 15 pairs built at
  the same level was flagged, and all 12 truly different pairs were.

  In practice the choice hardly matters for the headline. Marie Curtis and
  Sunnyside differ from every other beach by so much that any method would flag
  them. The choice affects only the borderline pairs among the six cleanest
  beaches.

  2D histogram. A square grid works too: plt.hist2d does exactly that.

  Hexagons are often preferred for three reasons:
  - All neighbours are equal. A hexagon touches 6 neighbours, each sharing a
    full edge at the same distance. A square has 4 edge neighbours and 4 corner
    neighbours that are farther away, so density looks slightly different along
    the diagonals than along the axes.
  - No false lines. A square grid lines up into straight rows and columns, and
    the eye tends to read those as horizontal and vertical structure in the
    data. Hexagons don't line up that way.
  - Closer to a circle. For the same area, a hexagon's corners are nearer its
    centre than a square's, so every point in a cell is closer to the spot it
    represents. The shading is a slightly more faithful picture of the density.

  Squares have one real advantage here: you can put a bin edge exactly at 100.
  In this plot, some hexagons straddle the dashed limit lines, so a few cells
  mix days over and under the limit. A square grid with edges at log10(100)
  would make each quadrant exactly match Table 2's counts. For judging the
  overall shape, as here, hexagons are the better choice. For reading off exact
  counts by quadrant, squares aligned with the limit would be.

❯ so with r~0.4, r^2 is 0.16. does that mean yesterday's data only explains 16% 
  of todays data?                                                               

⏺ Close, with a few qualifications. The numbers first: $0.42^2 \approx 0.18$ for
  all pairs, and $0.37^2 \approx 0.14$ once the pairs with both days at the
  floor are removed.

  What $r^2$ means. If you predict today's level with the best straight line
  through yesterday's level, $r^2$ is the share of today's variation that line
  accounts for. The other 82–86% is what the line misses, and it doesn't depend
  on yesterday.

  Four qualifications:
  1. It's the variation in log10 levels, not raw counts. On the log scale, a
     jump from 10 to 100 counts the same as one from 100 to 1,000.
  2. "Explains" is statistical, not causal. Yesterday's water doesn't cause
     today's. Both are pushed by the same things, such as a wet spell, and that
     shared influence is what the correlation picks up.
  3. The floor distorts it. Half the results are stuck at 10, so the true
     day-to-day relationship in the real E. coli levels is hidden. The first
     figure is inflated by pairs that agree only because both are at the floor.
     The second is probably understated, because the floor still flattens the
     low end. The true value is uncertain in both directions.
  4. The unexplained part isn't all real change. Some of it is measurement
     noise: five samples taken the same morning at one beach differ from each
     other, so even a perfect predictor couldn't match a single day's geometric
     mean exactly.

  What it means for the paper. Knowing yesterday tells you something about
  today, since $r^2$ is not zero, but most of today's level is new. That's the
  same message as Table 3, measured differently: the sign based on yesterday
  missed 63% of the days over the limit.

⏺ __init__.py marks the folder src/toronto_beaches_ecoli/ as a Python package,
  which is what lets the scripts and the paper write:

  What it does:
  - Makes the folder importable. Python treats a folder with an __init__.py as a
    package and each .py file inside it as a module. Here there is one module,
    analysis.
  - Runs when the package is first imported. Any code in it runs once. Ours
    holds only a one-line docstring describing the package, so importing does
    nothing else. Some projects use it to re-export functions, for example so
    that from toronto_beaches_ecoli import fit_beach_model works without the
    .analysis part. You don't need that.
  - It used to hold the hello-world main() from uv init, which we replaced with
    the docstring on Saturday.

  Why the import works from anywhere in the project. The code sits in src/, the
  "src layout". uv sync installs your own project into .venv in editable mode:
  Python is pointed at src/, so changes to analysis.py take effect immediately,
  with no reinstall. That's why scripts/06-…, scripts/07-… and the Python chunks
  in paper.qmd can all import the same functions, even though the paper runs

⏺ In this paper "gap" doesn't mean the confidence interval. It's the difference
  between a beach and the average beach sampled the same day, the $\beta_b$ in
  Equation 1. The Methods section defines it at first use: "$\beta_b$ is the
  beach's average gap from the others". It's plain English for what
  statisticians would call the difference or the effect, and the intervals
  describe the uncertainty around each gap. So "the gaps shown are smaller than
  the true gaps" means the beaches differ from each other by more than Figure 4
  shows, not that the intervals are too narrow.
